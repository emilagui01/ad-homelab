>_Invoke-LabBuild—☐✕

Build steps

PS C:\Labs\emillab> Invoke-LabBuild -Verbose

[1/6]Enable Hyper-V and create the lab network

Created an internal virtual switch and a NAT rule on the host so the lab stays isolated from my home network but can still reach the internet (needed to activate the evaluation OS).

# On the host laptop (JARVIS), elevated PowerShell
Enable-WindowsOptionalFeature -Online -FeatureName Microsoft-Hyper-V -All
New-VMSwitch -Name "LabSwitch" -SwitchType Internal
New-NetIPAddress -IPAddress 192.168.50.1 -PrefixLength 24 -InterfaceAlias "vEthernet (LabSwitch)"
New-NetNat -Name LabNAT -InternalIPInterfaceAddressPrefix 192.168.50.0/24

[2/6]Install Windows Server 2022 and configure DC01

Generation 2 VM, 2 vCPUs, 4 GB RAM, 60 GB disk. Renamed the server, assigned a static IP, and pointed DNS at itself in preparation for the DNS role.

Rename-Computer -NewName DC01 -Restart
New-NetIPAddress -InterfaceAlias "Ethernet" -IPAddress 192.168.50.10 -PrefixLength 24 -DefaultGateway 192.168.50.1
Set-DnsClientServerAddress -InterfaceAlias "Ethernet" -ServerAddresses 127.0.0.1
Set-TimeZone -Id "Central Standard Time"

[3/6]Promote DC01 to a domain controller

Installed Active Directory Domain Services and created a new forest, emillab.local, with integrated DNS. Took a Hyper-V checkpoint immediately after so the domain could be rolled back if later changes broke it.

Install-WindowsFeature AD-Domain-Services -IncludeManagementTools
Install-ADDSForest -DomainName "emillab.local" -InstallDns
Get-ADDomain   # verify the new domain

[4/6]Configure DNS forwarding and DHCP

Added a forwarder so domain clients can resolve internet names, then installed DHCP, authorized it in Active Directory, and created a scope that hands out the gateway and DC as DNS server.

Add-DnsServerForwarder -IPAddress 8.8.8.8
Install-WindowsFeature DHCP -IncludeManagementTools
netsh dhcp add securitygroups
Restart-Service dhcpserver
Add-DhcpServerInDC -DnsName dc01.emillab.local -IPAddress 192.168.50.10
Add-DhcpServerv4Scope -Name "Lab" -StartRange 192.168.50.100 -EndRange 192.168.50.200 -SubnetMask 255.255.255.0
Set-DhcpServerv4OptionValue -ScopeId 192.168.50.0 -Router 192.168.50.1 -DnsServer 192.168.50.10

[5/6]Create OUs and user accounts

Separated users and computers into their own organizational units so Group Policy can target each one later. Created three domain users.

New-ADOrganizationalUnit -Name "Lab Users"
New-ADOrganizationalUnit -Name "Lab Computers"
New-ADUser -Name "Jane Doe" -SamAccountName jdoe `
  -Path "OU=Lab Users,DC=emillab,DC=local" `
  -AccountPassword (Read-Host -AsSecureString "Password") -Enabled $true
# Repeated for John Smith (jsmith) and Peter Parker (pparker)

[6/6]Build CLIENT01 and join the domain

Windows 11 requires TPM 2.0 and at least two cores, so the VM got a virtual TPM before install. After setup it pulled an address from DHCP, joined the domain, was renamed to match its VM name, and was moved into the Lab Computers OU.

# On the host
Set-VMKeyProtector -VMName CLIENT01 -NewLocalKeyProtector
Enable-VMTPM -VMName CLIENT01
Set-VMProcessor -VMName CLIENT01 -Count 2

# On CLIENT01
Add-Computer -DomainName emillab.local -Credential emillab\Administrator -Restart
Rename-Computer -NewName CLIENT01 -DomainCredential emillab\Administrator -Restart

# On DC01
Get-ADComputer CLIENT01 | Move-ADObject -TargetPath "OU=Lab Computers,DC=emillab,DC=local"

Troubleshooting log

PS C:\Labs\emillab> Get-TroubleshootingLog

# Real problems hit during the build: symptom, root cause, and fix

New-ADUser : The specified account already exists

+ CategoryInfo : ResourceExists  |  after an earlier password complexity error

SymptomThe first attempt to create jdoe failed on password complexity. Retrying said the account already existed.
Root causeNew-ADUser creates the account object first, then sets the password. When the password was rejected, a disabled account with no password was left behind.
FixReset the password on the existing account and enabled it with Set-ADAccountPassword -Reset and Enable-ADAccount, then confirmed Enabled = True.

Get-ADComputer : Cannot find an object with identity: 'CLIENT01'

+ CategoryInfo : ObjectNotFound  |  after a successful domain join

SymptomThe client joined the domain, but AD had no computer named CLIENT01.
Root causeCLIENT01 was only the Hyper-V VM name. Windows setup had auto-named the computer DESKTOP-P26AUJ7, and that name joined the domain.
FixListed all computer objects with Get-ADComputer -Filter *, renamed the machine with Rename-Computer -DomainCredential, then moved it to the Lab Computers OU.

To sign in remotely, you need the right to sign in through Remote Desktop Services

+ Signing in to CLIENT01 as EMILLAB\jdoe

SymptomDomain Administrator could sign in to the client, but standard user jdoe was blocked.
Root causeHyper-V Enhanced Session mode connects over Remote Desktop. Standard users aren't in the Remote Desktop Users group by default.
FixSwitched the VM window to a basic session to sign in at the console. The long-term fix is granting a domain group Remote Desktop rights through Group Policy (planned).

WARNING: DC01 clock set to the wrong time zone

+ Found while reviewing the server after promotion

SymptomThe domain controller's clock was two hours behind local time.
Root causeThe server defaulted to Pacific time. Kerberos authentication depends on clocks staying in sync across the domain.
FixSet-TimeZone -Id "Central Standard Time" on DC01. Domain members sync time from the DC.

New-ADUser : The object name has bad syntax

+ Typos in commands

SymptomSeveral commands failed: a misspelled cmdlet, a missing closing quote, and a stray space before a parameter.
Root causeThe distinguished name used DC-emillab instead of DC=emillab. The error message pointed straight at the object name.
FixRead the error text closely and corrected each command. Lesson: PowerShell errors usually tell you exactly which part is wrong.
